# Content types

Read only the mode selected for the current artifact. These are craft criteria,
not new workflows or an instruction to produce every format.

## Docs and setup guidance

Follow the host repository's documentation structure/components. Start from the
reader's actual state: repository/version, role, prerequisites and configuration
that the selected task really needs. Explain action, observable result and useful
next step. Distinguish required from optional setup; do not imply setup is needed
merely to use a skill.

Order steps by dependency. A command needs its working directory and relevant
inputs; a configuration instruction needs the actual owner and safe example.
Explain how to recognize success and recover from the likely failure, including
what input or state is preserved. Put deeper implementation detail where it
helps extension or troubleshooting. Code validates the literal guide against
real source and the actual app/provider when required; keep unrun boundaries
visible. A successful local example does not prove every provider configuration.

### Help answers

Answer the specific question or give the first safe action immediately. Include
the condition under which it applies, exact steps or decision, expected result
and recovery if that result does not appear. A short answer can be complete;
do not add a marketing introduction, exhaustive architecture tour or generic FAQ.
Link the existing guide for broader setup. Preserve role, eligibility and
prerequisites even when shortening. If the cause is uncertain, distinguish the
observable symptom from the proposed diagnosis and choose a bounded next check.

## Articles and explanations

An article needs an actual decision, failure, tradeoff or evidence that supplies
a reusable lesson. A short founder observation can be a social post. Establish
why this reader should care now with a concrete consequence, recognizable problem
or revealing observation; avoid a generic industry preamble.

Write the reader promise and thesis, then outline the argument with a distinct
job for each section: orient the problem, explain a mechanism, compare a tradeoff,
show evidence or help apply the lesson. Use only the jobs the topic needs. Put a
useful inventory or compact answer early when readers need it to navigate or
apply the article. Deliver a numbered promise with actual distinct coverage.
Do not withhold all value until the final conclusion.

Build progressive value. An example should expose the mechanism or an important
exception; a figure should make a relationship easier to understand; a later
section should add depth rather than rename the opening claim. Show how facts
lead to the decision, what the alternative would change and where the lesson
stops transferring. Verify citations and separate implemented behavior from
observed outcomes. Choose structure around the reader's uncertainty rather than
a fixed introduction/problem/solution list.

## Social posts and founder updates

Use the requested audience/channel and delivered feature, proof or source.
Marketing supplies positioning. When a missing channel materially changes the
message, return that decision to Lead. For an explicitly requested general draft,
state that channel assumption and proceed without a distribution questionnaire.

Choose a specific hook: shipped work, failure, decision or useful lesson. Explain
the user-visible result concretely. Produce the requested amount; for an
unspecified small draft, recommend one strong post rather than automatic variants.
A thread adds evidence with each post instead of repeating a slogan.

Use links only when supplied/verified; otherwise label a link placeholder.
Do not invent screenshots, engagement metrics, testimonials or availability dates.
A helper-seeded demo is not a live paid customer story. Preserve limitations whose
omission would mislead. Use the founder's voice, not a starter vendor's voice;
hashtags/emojis require the founder's chosen voice. Return local drafts.
Posting/scheduling/contacting/spending needs explicit authority for that action.

## Scripts and captions

Name the viewer's question, supported action/result and what each beat contributes.
Writing owns words; Taste supplies consequential sequence/voice choices and actual
reference study. Separate captured behavior, seeded material, reconstruction and
fiction. A script/storyboard is a plan, not inspected playback or audience proof.
Check readability/timing with Code's actual production tools; disclose missing
capture, playback, sound or rights instead of promising a finished demonstration.
