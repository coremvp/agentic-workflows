# Launch

Load to connect a real release with the people it helps, the evidence they need,
and a useful encounter. A launch is a communication decision, not permission to
deploy or a reason to manufacture a campaign.

## Establish what can be offered

Inspect actual changed behavior, target users, eligibility, flags, availability,
setup and limitations. Product owns those facts. A committed branch, recorded
preview and shipped feature are different states. An actually available beta
can be announced as a beta with its real eligibility and limits; internal or
disabled work cannot be called available.

Choose the release's central user-visible change. Explain the previous obstacle,
new supported path and proof. If the change is an internal refactor without a
meaningful user effect, a public announcement may be unnecessary. A release of
several independent changes may need a digest rather than a forced grand story.

## Match effort to the decision

| Launch situation | Useful minimum | Dependency to resolve |
| --- | --- | --- |
| Small available improvement | Clear update + existing instructions if changed | Actual behavior and truthful availability |
| New supported user path | Explain eligibility, steps, result and recovery | Setup/documentation and end-to-end proof |
| Limited beta | Specific invitation for eligible users and limits | Real access, support/recovery owner |
| Larger product release | Proof-led explanation plus distinct supporting assets | Coherent offer, readiness and release ownership |

For a fictional export beta available only to opted-in paid workspaces, say who
can use it and what is excluded. Do not announce universal export or promise a
GA date unsupported by Product.

## Plan the encounter, not every channel

Recommend the audience, argument/proof, primary encounter, next action and
necessary assets. Reuse existing explanation/capture where sufficient. Use
[content promotion](content-promotion.md) when complementary encounter jobs
matter and [release communication](release-communication.md) for changes-to-copy
translation. Writing drafts the selected output; Taste supports consequential
composition/voice; Code produces authorized media and actual checks.

Before communication promises an action, use [launch readiness](launch-readiness.md)
for unresolved links, forms, eligibility, proof and recovery. If a dependency is
missing, finish a draft with a visible hold and owner; do not conceal it with
optimistic wording. Publishing, schedules, outreach, paid calls and production
have their own authority. After actual release, inspect available response with
baseline/context; no response means no fabricated learning.
