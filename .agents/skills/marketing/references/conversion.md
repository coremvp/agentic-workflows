# Conversion

Load to diagnose a specified journey from encounter to useful completed action.
Identify the actor, starting state, promised result, next action and actual
outcome. Conversion may mean finishing setup, completing an operator task or
requesting a useful demo, not only paying. Fit the goal to Product truth and
user interests; do not impose a commercial funnel on every application.

## Locate the failing stage

Name the first useful outcome, not merely the next button. Is the actual problem
reaching suitable people, understanding the offer, deciding to try, completing
the attempt, obtaining that first useful result, or returning when the job recurs?
Use only stages present in the real journey. A signup can succeed while setup
remains blocked; a CLI can install while its documented command still fails.

Inspect supplied analytics/events, current page/form behavior, errors and entry
context. Separate exposure, eligible attempt, durable completion and actual
useful result where those differ. A redirect or click can differ from a recorded
success. Retain source, period, denominator, cohort and instrumentation gaps.
Do not diagnose a drop-off from percentages without knowing who could take the
next step or whether events represent the promised result.

## Diagnose the obstacle before changing the surface

| Friction | Evidence to seek | Bounded candidate |
| --- | --- | --- |
| Wrong expectation or unsuitable audience | Message/traffic mismatch, unsuitable requests | Clarify audience/result or reconsider encounter |
| Missing trust or commitment clarity | Specific question about cost/data/next step | Put the supported answer near its decision |
| Comprehension | Misread labels, missed condition | Clarify the choice and inspect actual interaction |
| Unnecessary work | Required data/setup unused for the useful result | Remove/defer only after owner/requirement inspection |
| Failure/recovery | Validation, lost input, duplicate attempts, failed command | Development/Frontend repairs actual behavior under authority |
| No first useful outcome | Completed setup but blocked task or missing next step | Inspect the minimum supported path to value |
| Product mismatch | Understood offer cannot do needed task | Product decision; copy cannot repair missing capability |
| No continued use | Initial value exists but recurring job, fit or reliability is unclear | Inspect the actual recurrence and later experience |

Rank hypotheses by evidence and consequence, and keep competing explanations.
A rarely recurring job does not imply failed retention; an unsuitable visitor
leaving can be correct. Do not shorten required authorization, billing or safety
steps to increase a surface completion count. Use [form optimization](form-optimization.md)
for field-level judgment and Frontend for actual interaction decisions.

For fictional trial requests, losing entered company details after an email
validation error supports a recovery diagnosis. It does not prove removing
company details increases qualified trials, or that all existing labels are wrong.
If the trial then opens an empty workspace with no supported first task, that is
a separate first-value question, not evidence for another button color.

## Hand off a testable change

Return the affected stage and outcome, observed issue, alternative explanation,
proposed bounded change, why, proof need and outcome/guardrail. Prefer removing
the demonstrated obstacle over redesigning the whole journey. Frontend owns
unsettled application design; Development/Code own authorized implementation and
actual checks. Marketing never silently mutates a form or calls analytics providers.

Use [A/B testing](ab-testing.md) when a controlled comparison could change the
decision. A reproducible bug should be repaired and verified; low-information
traffic may call for task observation instead. Distinguish local behavior proof
from later customer outcomes. State uncertainty without promising lift,
significance or revenue causality.
