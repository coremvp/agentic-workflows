# SEO audit

Load to diagnose a bounded discoverability/intent problem. Start with the actual
page/site, intended public/private status, reader question and supplied evidence.
An audit recommendation is not authority to crawl private areas or edit the app.

## Define the symptom and usable evidence

Name what is observed: a missing URL, wrong result, blocked answer, wrong locale,
misleading title, lost impressions or poor qualified response. Record page/query,
period, environment and affected context where known. “SEO is bad” is not yet a
diagnosis. Start with a representative affected owner and a relevant working
comparison; expand only when the evidence points to a shared defect.

| Evidence | Can establish | Cannot establish alone |
| --- | --- | --- |
| Source/config | Intended route/metadata behavior | Live response or indexed result |
| Response: raw HTML, status and headers | What that response delivered | Every post-render state |
| Stripped text | Extracted readable content | Absence of scripts, schema or hidden markup |
| Rendered DOM | Present browser markup at inspected state | Crawler/indexing/permission behavior everywhere |
| Search report | Reported query/page impressions/clicks in period | Complete demand, causality or all competitors |
| Search result sample | Observed result/intent for a context | Permanent ranking or universal user intent |

If a text extractor omitted JSON-LD, do not declare structured data missing.
Inspect appropriate raw/rendered evidence through Code when authorized, or mark
the gap. Missing proof is not proof of absence. Keep source/date and real,
fixture-backed or replayed scope explicit.

## Diagnose in dependency order

Select the first layer capable of explaining the symptom. Verify a demonstrated
upstream obstruction before polishing downstream copy; a narrow content question
need not become a whole-site technical audit.

| Layer | Investigation and consequence |
| --- | --- |
| Access and status | Does the exact URL resolve, redirect or fail? Who can retrieve the useful answer, in which environment? A browser login state is not a crawler-access test. |
| Discovery and indexability | Is this intended public material in the actual link/inventory owner? Compare robots directives, response/page indexing signals and known provider evidence. Discovery, crawl and indexing remain separate states. |
| Canonical and locale | Do redirects, canonical targets, origins, alternates and inventory agree on the intended answer? Inspect actual target availability and equivalence before consolidating. |
| Delivered answer | Does the appropriate response/render contain the useful content? Compare source intent with the representation relevant to the claim. |
| Intent and content | Does the answer satisfy the observed question and starting state? What supported explanation, proof, action or recovery is missing? Is an existing owner stronger? |
| Title and presentation | Do title, heading, description, preview and visible answer represent the same job? Low CTR can have explanations beyond wording. |
| Useful outcome | What happens after the eligible reader arrives? A click is not task completion or revenue; hand off actual behavior failures to their owner. |

Private access relies on server authorization, not robots directives. Structured
data describes the visible truthful page; its presence or validation alone does
not prove indexing or rich-result display. Framework-specific fixes need the
actual installed owner/version and compatible official documentation.

Use [title tags](title-tags.md), [search opportunities](search-opportunities.md),
[international SEO](international-seo.md) or [local SEO](local-seo.md) only when
the corresponding uncertainty is present.

## Correct the smallest actual owner and verify it

For each material finding connect observed evidence, alternative explanation,
user/discovery consequence, actual owner, bounded change and verification. Separate
a proven wrong canonical from a hypothesis about low click-through. Prefer
repairing a broken useful owner to adding keyword pages. Do not invent traffic
forecasts, ranking gains or health scores.

Verify the correction through the owner that creates the output: generated
metadata, actual status/redirect, public inventory, delivered answer or content
claim as appropriate. Include a relevant reject/private/locale case when changing
that boundary. Code executes checks and authorized edits; Review reads source
and recorded evidence independently. Reuse unchanged proof and distinguish
source inspection, local response, live route and provider indexing evidence.

State which symptom is explained, which correction is proved and which later
search outcome remains unknown. Use existing authorized reports for later
measurement with a comparable baseline and attribution limits. No whole-site
crawl, recurring monitor, vendor setup or publication is implied.
